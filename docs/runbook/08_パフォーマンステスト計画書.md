# 8. パフォーマンステスト計画書

vLLMでモデルを自前ホストする構成 (Dify + LiteLLM + vLLM) 向けの性能テスト計画書。
実施手順は「9. パフォーマンステスト手順書」、結果記入は「10. パフォーマンステスト結果記録」を使う。

- **対象システム**: `<SYSTEM_NAME>` (Dify + LiteLLM + vLLM)
- **対象モデル**: `<VLLM_MODEL_ID>` (LiteLLM側のモデル名: `<MODEL_NAME>`)
- **作成者 / 作成日**: `<CREATED_BY>` / `<CREATED_DATE>`

置き換え: `<SYSTEM_NAME>` `<MODEL_NAME>` `<VLLM_HOST>` `<VLLM_PORT>` `<VLLM_MODEL_ID>`
`<VLLM_SERVED_MODEL_NAME>` `<VLLM_TOKENIZER_PATH>` `<VLLM_MODELS_DIR>` `<VLLM_BENCH_IMAGE>`
`<VLLM_CONTAINER_NAME>` `<BENCH_REPO_DIR>` `<DIFY_HOST>` `<DIFY_PORT>`
`<LITELLM_HOST>` `<LITELLM_PORT>` `<CREATED_BY>` `<CREATED_DATE>`。

> ⚠️ vLLMのAPIとメトリクスは同じ `<VLLM_PORT>` で公開している前提です。
> 別ポートで運用している場合は、該当箇所を個別に読み替えてください。
>
> ⚠️ 4.3節のVRAM/KVキャッシュの理論計算は、GPU「H100 NVL×2 (188GB VRAM)」・
> モデル「Gemma 4 31B FP8-block」を前提にした**計算例**です。異なるGPU/モデル構成で
> 実施する場合は、4.2〜4.3節の数値・計算式を実環境に合わせて設計し直してください。

## 1. 目的とスコープ

### 1.1 目的

Step1 構成における以下を実測し、Step2以降の判断材料とする。

1. **ボトルネックの特定** — どのレイヤーが性能限界を決めているか
2. **飽和点の把握** — 同時実行数がどこまで伸ばせるか
3. **許容範囲の定義** — 実用に耐えるレイテンシの上限と、そのときの収容ユーザー数

### 1.2 スコープ

**含む**
- vLLM 単体の推論性能（理論限界）
- Dify 経由での E2E 性能測定
- 入力／出力トークン長を変えた場合の性能変化
- GPU リソース（使用率・VRAM・KVキャッシュ）の挙動
- **Dify・LiteLLM の OS／コンテナリソース挙動**

**含まない**
- 長時間の耐久試験（24h以上）
- 障害注入試験（chaos testing）
- マルチノード分散推論

### 1.3 合格基準の考え方

本テストは **合格 / 不合格の判定を目的としない**。Step1 の位置づけに従い、
「この構成の実力値は X である」を記録し、Step2以降のサイジング根拠及び、運用時の負荷判断指標とする。

## 2. 前提：ボトルネックはvLLMに集約される

| レイヤー | 性能特性 | ボトルネックになるか |
|---|---|---|
| Dify | I/Oバウンド（DB・Redis・HTTPプロキシ） | 通常ならない |
| LiteLLM | HTTPプロキシ（オーバーヘッド数ms〜数十ms） | 通常ならない |
| **vLLM + H100 NVL×2** | **GPU計算・KVキャッシュがリソース制約** | **濃厚** |

したがって本テストは「vLLM の限界を測る」ことを主眼としつつ、Dify・LiteLLM を
通した**E2Eの実測値**（利用者が実際に体感する値）を合わせて把握することを目的とする。

> 「通常ならない」という想定はあくまで仮説であり、フェーズ3のE2E実測で
> ボトルネックが疑われた場合は、7節のDify・LiteLLM側リソース監視で
> 実際にCPU/メモリが逼迫していないかを裏付けとして確認する。

## 3. 測定指標

### 3.1 LLM 固有の指標

| 指標 | 定義 | 何に効くか | 取得元 |
|---|---|---|---|
| **TTFT** (Time To First Token) | リクエスト送信〜最初のトークン受信 | 体感速度。プリフィル処理＝**入力トークン数に比例** | フェーズ1・2: `vllm bench serve` の `mean/median/p50/p90/p99_ttft_ms` / フェーズ3: LiteLLM 記録（UI「Logs」） |
| **TPOT** (Time Per Output Token) | 2トークン目以降の平均間隔 | 読む速度の体感。**同時実行数の影響を受ける** | フェーズ1・2: `*_tpot_ms` / フェーズ3: LiteLLM 記録から算出 |
| **ITL** (Inter-Token Latency) | トークン間隔の分布 | 生成の滑らかさ。スパイク検出 | フェーズ1・2: `*_itl_ms`（**TPOT とは別に出力される**） |
| **LLM区間Duration** | LiteLLMへのリクエスト送信〜応答完了 | vLLM＋LiteLLM区間のみの実力値 | フェーズ3: LiteLLM 記録（UI「Logs」） |
| **E2Eレイテンシ** | リクエスト送信〜完了 | 利用者が実際に体感する値 | フェーズ1・2: `*_e2el_ms`（**`--percentile-metrics` に `e2el` を明示しないと出ない**） / フェーズ3: Locust実測 |
| **スループット** | 出力トークン/秒・総トークン/秒 | 収容可能ユーザー数の根拠 | フェーズ1・2: `output_throughput` / `total_token_throughput` / フェーズ3: LiteLLM 記録から算出 |
| **キュー待ち時間** | リクエストが待機した時間 | **飽和点の判定に使用** | フェーズ1・2: vLLM `/metrics` の `vllm:request_queue_time_seconds`（ヒストグラム） |
| **スキーマ適合率** | 構造化出力が JSON Schema に適合した割合 | **Dify から使えるかの実質的な合否** | `bench/validate_structured.py` |

> 一般的な Web 負荷試験の「RPS」は LLM では意味が薄い。**トークン/秒**で評価する。

> フェーズ3（Dify経由のE2E測定）では、LiteLLMが既にリクエスト単位でTTFT相当・Duration・トークン数を記録しているため、
> Locustは**E2E（Dify全体の応答完了までの時間）とエラー率のみ**を計測し、
> LiteLLMの記録と突き合わせて **Dify自身の処理時間（E2E − LLM区間Duration）** を算出する。

### 3.2 リソース指標

| 指標 | 取得方法 |
|---|---|
| GPU 使用率 / 温度 / VRAM | `nvidia-smi --query-gpu=utilization.gpu,temperature.gpu,memory.used --format=csv -l 2` |
| **KVキャッシュ使用率** | vLLM `/metrics` の **`vllm:kv_cache_usage_perc`** |
| 実行中/待機中リクエスト数 | `vllm:num_requests_running` / `vllm:num_requests_waiting` |
| キュー待ち時間 | `vllm:request_queue_time_seconds_bucket`（ヒストグラム） |
| **プレフィックスキャッシュヒット率** | `vllm:prefix_cache_hits_total` ÷ `vllm:prefix_cache_queries_total` |
| **Dify VM の OS リソース**（CPU/メモリ/ロードアベレージ） | `vmstat` / `sar`（7.3節） |
| **Dify コンテナ別リソース**（api/worker/web等） | `docker stats`（7.3節） |
| **LiteLLM VM の OS リソース** | `vmstat` / `sar`（7.4節） |
| **LiteLLM コンテナリソース** | `docker stats`（7.4節） |

## 4. トークンプロファイル設計

### 4.1 なぜ入力/出力を分けるか

vLLM の処理は2段階で、負荷特性が全く異なる。

| 段階 | 処理内容 | 特性 |
|---|---|---|
| **Prefill**（入力処理） | 入力トークンを一括処理 | 計算集約的。**入力が長いと TTFT が伸びる** |
| **Decode**（出力生成） | 1トークンずつ生成 | メモリ帯域律速。**同時実行数が増えると TPOT が伸びる** |

「入力8,000トークン×同時5」と「入力500トークン×同時50」ではボトルネックが異なるため、
両方を測定しないと実態が掴めない。

### 4.2 プロファイル定義

`--max-model-len=12288`（vLLM起動時の実測確定値）を前提とする。
**プロファイルは全て `bench/make_dataset.py` (`<BENCH_REPO_DIR>` 配下) で生成します。**

| ID | プロファイル | 入力 | 出力 | 合計 | 生成コマンド（<BENCH_REPO_DIR> で実行） |
|---|---|---|---|---|---|
| **A** | 短文QA | 200 | 200 | 400 | `--only rate --rate-input-tokens 200 --rate-output-tokens 200 --rate-name profile-A.jsonl` |
| **B** | **RAG標準** | **3,000** | **500** | 3,500 | `--only rate --rate-input-tokens 3000 --rate-output-tokens 500 --rate-name profile-B.jsonl` |
| **C** | RAG大 | 10,900 | 800 | 11,700 | `--only rate --rate-input-tokens 10900 --rate-output-tokens 800 --rate-name profile-C.jsonl` |
| **D** | 長文生成 | 800 | 3,000 | 3,800 | `--only rate --rate-input-tokens 800 --rate-output-tokens 3000 --rate-name profile-D.jsonl` |
| **E** | 限界テスト（連続投入） | **約 9,400**（15,000文字） | **256** | **約 9,700** | `--only soak --soak-chars 15000` → `soak-15k.jsonl` |
| **F** | **レート目標**（20万tok/分） | 3,072 | 1,024 | 4,096 | `--only rate`（既定）→ `rate-target.jsonl` |
| **S** | **構造化出力**（Dify想定） | 551 / 1,010 / 4,083 | 上限1,024 | — | `--only structured` → `gemma4-structured.jsonl` |

### 4.3 KVキャッシュ容量からの理論値

H100 NVL×2 = 188GB VRAM、`--gpu-memory-utilization 0.92` の場合：

```
利用可能VRAM          ≈ 173 GB
モデル重み(31B FP8)    ≈  31 GB   ※FP8は1パラメータ≒1バイト換算
KVキャッシュ用         ≈ 142 GB
```

Gemma 4 31B FP8-block（GQA構成）のKVキャッシュを 1トークンあたり 0.10MB と仮定
（KVキャッシュ自体は多くの実装でFP16/BF16のまま保持されるため、重みほど圧縮率は高くない）：

```
142 GB ÷ 0.10 MB ≈ 1,420,000 トークン分
```

| プロファイル | 1リクエストの消費 | 理論同時実行数 |
|---|---|---|
| A（400トークン） | 0.04 GB | 数百並列（実際は`--max-num-seqs`とCPU側で頭打ち） |
| **B（3,500トークン）** | **0.35 GB** | **約400並列（実質は`--max-num-seqs`が上限）** |
| C（11,700トークン） | 1.17 GB | 約120並列 |
| **E（10,988トークン・`--max-model-len`付近）** | **1.10 GB** | **約129並列（理論値。実際は`--max-num-seqs`で頭打ち）** |

> **FP8-blockモデルはVRAMに大きな余裕がある**ため、KVキャッシュ制約よりも
> `--max-num-seqs`（既定64）やGPU計算能力（FP8 Tensor Core のスループット）が
> 先に上限となる可能性が高い。ただしEプロファイルは1リクエストのKVキャッシュ
> 消費が大きいため、**連続投入時はB・Cよりも早くKVキャッシュ使用率が
> 上限に達する**可能性がある。フェーズ2でこの点を重点的に観察する。

実測値はログに出力されているため、下記コマンドで取得可能  
```bash
docker logs <VLLM_CONTAINER_NAME> 2>&1 | grep -iE "Available KV cache memo"
```

## 5. 使用ツール

| ツール | 何を測るか | 対象 |
|---|---|---|
| **`bench/make_dataset.py`** | **測定に使うデータセットを生成** | 事前準備 |
| **`vllm bench serve`**（vLLM同梱CLI） | GPU単体の理論限界（TTFT/TPOT/ITL/E2EL/スループット） | vLLM 直接 |
| **`bench/validate_structured.py`** | 構造化出力のスキーマ適合率 | 結果JSONを事後解析 |
| **`bench/throughput_target.py`** | レート目標の計画（必要req/s）と達成判定 | 結果JSONを事後解析 |
| **`bench/summarize.py`** | 複数runの横並び比較 | 結果JSON |
| **Locust** | **E2E**＝利用者が実際に体感する値 | Dify API |
| `nvidia-smi` | GPU監視 | 全フェーズで並行実行 |
| vLLM `/metrics` | キュー長・KVキャッシュ使用率・プレフィックスキャッシュヒット率 | 飽和点判定 |
| `vmstat` / `sar` | **Dify・LiteLLM VM の OS リソース監視** | フェーズ3で並行実行 |
| `docker stats` | **Dify・LiteLLM の コンテナ別リソース監視** | フェーズ3で並行実行 |

2ツールは測定対象が異なる別軸：**CLIでGPUの理論限界を出し、LocustでDify経由のE2E実測値を出す**。
両者を突き合わせることで「GPU理論値に対してE2Eがどれだけ乗っているか」を把握する。

### 5.1 `bench/make_dataset.py`（データセット生成）

4.2 節のプロファイルを実ファイル（JSONL）に落とすスクリプトです。
`vllm bench serve --dataset-name custom` が読む形式（`prompt` 列 + `output_tokens` 列）で出力します。

```bash
# 既定の4種をまとめて生成
.venv-bench/bin/python bench/make_dataset.py \
  --tokenizer <VLLM_TOKENIZER_PATH> \
  --out-dir bench/datasets/h100

# プロファイル単位で作り分ける（4.2節の表を参照）
.venv-bench/bin/python bench/make_dataset.py --only rate \
  --rate-input-tokens 3000 --rate-output-tokens 500 --rate-name profile-B.jsonl
```

やっていること:

| 機能 | なぜ必要か |
|---|---|
| **実トークナイザで計測しながら生成** | 「入力3,000トークン」を**文字数からの概算ではなく実測で合わせる**。設計値と実測がずれない |
| **モデルごとに作り直せる**（`--tokenizer`） | Gemma と Qwen ではトークナイザが違い、同じ本文でもトークン数が変わる。使い回すと長さ設計が崩れる |
| **行ごとに内容を変える** | 先頭に一意のID、段落順もシャッフル。**プレフィックスキャッシュが効くと TTFT が実力より良く出る**ため |
| **スキーマ本文をプロンプトに埋め込む**（構造化用） | これが無いとモデルが必須フィールドを知らず、空白ループで打ち切られる（4.4節・実測で適合率 21.7%） |
| **生成時に長さを表示** | `prompt + output` が `--max-model-len` に収まるかをその場で確認できる |

主なオプション:

| オプション | 既定 | 用途 |
|---|---|---|
| `--tokenizer` | Gemma 4 E4B を自動検出 | tokenizer.json のパス / ディレクトリ / glob を受け付ける |
| `--out-dir` | `bench/datasets` | 出力先。モデルごとに分ける |
| `--only` | 全種 | `general` / `structured` / `soak` / `rate` のいずれかだけ生成 |
| `--rate-input-tokens` / `--rate-output-tokens` | 3072 / 1024 | **プロファイル A〜D・F の入出力トークン数** |
| `--rate-name` | `rate-target.jsonl` | プロファイルごとにファイル名を分ける |
| `--soak-chars` | 15000 | プロファイル E の1件あたり文字数 |
| `--soak-count` / `--rate-count` | 100 / 200 | 件数。**連続投入を長くするならここを増やす** |
| `--seed` | 固定 | 生成は決定的。同じ引数なら同じ内容になる |

> [!NOTE]
> `bench/schemas/dify-triage.schema.json` を**相対パスで参照**するため、
> 必ず <BENCH_REPO_DIR> から実行してください。
> 外部依存は `tokenizers` のみです（他の3スクリプトは標準ライブラリだけで動きます）。

## 6. テスト実施計画
### 共通のコマンド形（フェーズ1・2）
```bash
BENCH() {   # BENCH <dataset> <result-name> <追加オプション...>
  local ds=$1 name=$2; shift 2
  docker run --rm --network host -e HF_HUB_OFFLINE=1 \
    -v "$PWD/bench:/bench" -v "<VLLM_MODELS_DIR>:/root/.cache/huggingface:ro" \
    <VLLM_BENCH_IMAGE> \
    vllm bench serve \
      --backend openai-chat --base-url http://localhost:<VLLM_PORT> \
      --endpoint /v1/chat/completions \
      --model <VLLM_MODEL_ID> --served-model-name <VLLM_SERVED_MODEL_NAME> \
      --dataset-name custom --dataset-path "/bench/datasets/h100/${ds}" \
      --custom-output-len -1 --skip-chat-template --disable-shuffle --no-oversample \
      --num-warmups 3 --disable-tqdm \
      --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,90,99 \
      --save-result --save-detailed \
      --result-dir /bench/results --result-filename "${name}.json" "$@"
}
```
### フェーズ1：単体性能（ベースライン取得）

**目的**: 並列1における理論最速値を取得し、以降の比較基準とする

| # | テスト内容 | 経路 | 並列 | プロファイル |
|---|---|---|---|---|
| 1-1 | ベースライン測定 | vLLM直接 | 1 | B |
| 1-2 | 入力長の影響測定 | vLLM直接 | 1 | A / C / D |
| 1-3 | 上限確認（単発） | vLLM直接 | 1 | E |
| **1-4** | **構造化出力の適合率** | vLLM直接 | 1 | **S** |

```bash
BENCH profile-B.jsonl phase1_B_c1 --num-prompts 20 --max-concurrency 1 --ignore-eos
BENCH profile-A.jsonl phase1_A_c1 --num-prompts 20 --max-concurrency 1 --ignore-eos
BENCH profile-C.jsonl phase1_C_c1 --num-prompts 20 --max-concurrency 1 --ignore-eos
BENCH profile-D.jsonl phase1_D_c1 --num-prompts 20 --max-concurrency 1 --ignore-eos
BENCH soak-15k.jsonl  phase1_E_c1 --num-prompts 10 --max-concurrency 1

# 1-4: 構造化出力（--ignore-eos は付けない）
BENCH gemma4-structured.jsonl phase1_S_c1 --num-prompts 60 --max-concurrency 1 \
  --extra-body "$(cat bench/schemas/dify-triage.extra-body.json)"
python3 bench/validate_structured.py bench/results/phase1_S_c1.json
```

**記録項目**: TTFT (P50/P90/P99)、TPOT、ITL、E2Eレイテンシ、出力トークン/秒、**スキーマ適合率(1-4)**

### フェーズ2：飽和点の特定 ★最重要

**目的**: 同時実行数をどこまで伸ばせるか、どこで性能が崩れるかを特定

| # | テスト内容 | 経路 | 負荷の振り方 |
|---|---|---|---|
| 2-1 | 段階的負荷（B） | CLI（vLLM直接） | `--request-rate`: 1 → 2 → 5 → 10 → 20 → 40 → 80 → inf |
| 2-2 | 段階的負荷（C） | CLI（vLLM直接） | `--request-rate`: 1 → 2 → 5 → 10 → 20 → 40 → inf |
| 2-3 | **長文連続投入**（E） | **CLI（vLLM直接）** | `--max-concurrency`: 1 → 2 → 4 → 8 → 16 |
| **2-4** | **レート目標**（F） | CLI（vLLM直接） | 目標レート固定 |
| **2-5** | **負荷下の構造化出力**（S） | CLI（vLLM直接） | `--max-concurrency`: 8 → 16 |
| 2-6 | Dify経由のE2E（E） | Locust（Dify経由） | 同時実行: 1 → 3 → 5 → 10 |

> FP8-blockはKVキャッシュに余裕があるため、実際の上限は `--max-num-seqs`（既定64）や
> GPU計算能力側で先に頭打ちになる可能性が高い。理論値（B:約400並列、C:約110並列）を
> 鵜呑みにせず、レンジを広めに取って実測すること。

**飽和点の判定基準**
> `vllm:num_requests_waiting` が **継続的に 0 より大きくなった時点** を飽和点とする。
> あわせて `vllm:kv_cache_usage_perc` と `vllm:request_queue_time_seconds` の推移を記録する。

**記録項目（2-1・2-2）**: TTFT (P50/P95/P99)、TPOT、キュー待ち時間、KVキャッシュ使用率、GPU使用率、エラー率

#### 2-3. 長文連続投入（プロファイルE）

**背景**：「1万5000文字程度のテキストを入れ続け、何回連続できるか」という試験条件に対応します。
単発の上限確認（1-3）とは別に、持続投入時の挙動（KVキャッシュ枯渇・エラー発生点・レイテンシ悪化）を見ます。

```bash
for C in 1 2 4 8 16; do
  BENCH soak-15k.jsonl "phase2_E_c${C}" --num-prompts 100 --max-concurrency $C
  sleep 60
done
```

> [!IMPORTANT]

### 7.3 Dify VM のリソース監視

**目的**：フェーズ3のE2E測定中、Dify自身の処理（ワークフロー実行・RAG検索・
SSE変換）がDify VM側のCPU/メモリ逼迫によって遅くなっていないかを確認する。
「Dify自身の処理時間（E2E − LLM区間Duration）」が大きい場合、原因がここにあるか
どうかの一次切り分けに使う。

#### OSリソース（CPU・メモリ・ロードアベレージ、1秒間隔）

```bash
# vmstat: CPU使用率・メモリ・スワップ・実行待ちプロセス数
vmstat 1 > dify_vmstat_$(date +%Y%m%d_%H%M).log &

# sar が使える場合はより詳細に (CPU/メモリ/ロードアベレージを分離取得)
sar -u -r -q 1 > dify_sar_$(date +%Y%m%d_%H%M).log &
```

`vmstat`の見るべき列：`r`（実行待ちプロセス数。CPUコア数を継続的に超えていたらCPUが律速）、
`free`（空きメモリ）、`si`/`so`（スワップ発生。0でなければメモリ不足の兆候）。

#### コンテナ別リソース（api/worker/web等）

Difyは複数コンテナ（api / worker / web / plugin_daemon 等）で構成されるため、
コンテナ単位でCPU・メモリを分離してCSV形式で取得する。**どのコンテナがボトルネック
かの特定**に加え、**7.5節のスケール算出にそのまま使える形**で記録する。

```bash
# dify_docker_stats.sh
# 1秒間隔、CSVヘッダ付き。docker stats の CPUPerc は「コンテナに見えているCPU数」
# に対する割合である点に注意（--cpus=2 のコンテナなら上限200%）。
OUT="dify_docker_stats_$(date +%Y%m%d_%H%M).csv"
echo "timestamp,container,cpu_perc,mem_usage,mem_limit,mem_perc" > "$OUT"
while true; do
  TS=$(date +%s)
  docker stats --no-stream --format '{{.Name}},{{.CPUPerc}},{{.MemUsage}},{{.MemPerc}}' \
    | awk -F',' -v ts="$TS" '{
        split($3, m, " / ");
        gsub("%","",$2); gsub("%","",$4);
        print ts","$1","$2","m[1]","m[2]","$4
      }' >> "$OUT"
  sleep 1
done
```

> Difyの`worker`コンテナ（Celery）がRAG検索やワークフロー実行の実処理を担うため、
> フェーズ3でE2Eが伸びている場合、**`worker`コンテナのCPU使用率が張り付いていないか**
> を最初に確認する。`api`コンテナはHTTP受付が主であり、通常はここが先に詰まることは少ない。

#### 各コンテナの現在の割当（CPU/メモリ制限）を控えておく

`docker stats`のCPU%・MEM%は**制限値に対する割合**なので、スケール算出には
「現在何を割り当てているか」が必須の前提情報になる。実行前に確認しておく。

```bash
docker inspect --format \
  '{{.Name}},{{.HostConfig.NanoCpus}},{{.HostConfig.Memory}}' \
  $(docker ps -q) | sed 's/^\///'
# NanoCpus: 1コア=1000000000（例: 2000000000 なら 2vCPU）
# Memory: バイト単位（例: 4294967296 なら 4GiB）。0 は無制限
```

#### PostgreSQL（pgvector）の長時間クエリ（RAG検索の切り分け用）

```sql
-- Dify用PostgreSQLに接続して実行
SELECT pid, now() - query_start AS duration, state, query
FROM pg_stat_activity
WHERE state = 'active' AND now() - query_start > interval '1 second'
ORDER BY duration DESC;
```

3-3（RAGあり/なし比較）の差分が大きい場合、ここでベクトル検索クエリの実行時間を
直接確認できる。

### 7.5 コンテナメトリクスからのスケール算出

**目的**：7.3節で取得した`dify_docker_stats_*.csv`から、各コンテナのピークCPU%・
MEM%を集計し、**目標使用率に収めるために必要なvCPU/メモリ割当（垂直スケール）**、
および**目標同時実行数を捌くために必要なレプリカ数（水平スケール）の目安**を算出する。
本番要件（Step2）のリソースサイジング根拠として使う。

#### 7.5.1 CSVからのピーク・平均値集計

```bash
python3 - <<'EOF'
import csv
from collections import defaultdict

rows = defaultdict(list)
with open("dify_docker_stats_YYYYMMDD_HHMM.csv") as f:
    for r in csv.DictReader(f):
        rows[r["container"]].append(r)

print(f"{'container':<25} {'cpu_peak%':>10} {'cpu_avg%':>10} {'mem_peak%':>10} {'mem_avg%':>10}")
for name, recs in rows.items():
    cpu = [float(r["cpu_perc"]) for r in recs]
    mem = [float(r["mem_perc"]) for r in recs]
    print(f"{name:<25} {max(cpu):>10.1f} {sum(cpu)/len(cpu):>10.1f} {max(mem):>10.1f} {sum(mem)/len(mem):>10.1f}")
EOF
```

出力例：

```
container                  cpu_peak%   cpu_avg%   mem_peak%   mem_avg%
dify-worker-1                   184.2       92.5        68.3       55.1
dify-api-1                       42.7       18.3        31.0       28.4
dify-web-1                        8.1        3.2        12.5       11.8
```

#### 7.5.2 垂直スケール算出（必要vCPU/メモリの逆算）

現在の割当（7.3節`docker inspect`で確認済み）と実測ピークから、
**目標使用率**（推奨: 70%。ピーク時でも余裕を残す）に収めるための必要量を逆算する。

```
必要vCPU数 = 現在の割当vCPU数 × (実測ピークCPU% ÷ 目標CPU%)
必要メモリ = 現在の割当メモリ × (実測ピークMEM% ÷ 目標MEM%)
```

**計算例**（`dify-worker-1`が2vCPU割当でピークCPU 184%、目標70%の場合）：

```
必要vCPU数 = 2 × (184 ÷ 70) = 5.26 → 6vCPU に増強
```

この計算は「10. パフォーマンステスト結果記録」の`Difyコンテナスケール算出`シートで
自動化する（7.5.4節参照）。

#### 7.5.3 水平スケール算出（レプリカ数の目安）

CPU使用率が既に上限（`--max-num-seqs`や`--cpus`制限）に張り付いており、
垂直スケール（1コンテナの増強）では収まらない規模の負荷を想定する場合、
レプリカ数の目安を以下で算出する。

```
必要レプリカ数 = CEILING(目標同時実行数 ÷ 実測で1レプリカが処理できた実効同時実行数)
```

「実測で1レプリカが処理できた実効同時実行数」は、フェーズ2（F2_飽和点_B等）で
判定した「快適」または「許容」の上限値（ベースライン比3倍未満の最大同時実行数）を使う。

**計算例**：1レプリカで同時実行10まで「許容」、本番で同時実行50を捌きたい場合

```
必要レプリカ数 = CEILING(50 ÷ 10) = 5レプリカ
```

> worker（Celery）はDify公式が水平スケール対応（`docker compose up --scale worker=N`）
> をサポートしている。api/webコンテナも同様にスケール可能。ただしPostgreSQL・Redisは
> 単純なレプリカ増では対応できないため、レプリカ数を増やす場合は7.3節のPostgreSQL
> 長時間クエリ確認とセットでDB側の余力も確認すること。

#### 7.5.4 Excelでの自動算出

「10. パフォーマンステスト結果記録」の`Difyコンテナスケール算出`シートに、
7.5.1の集計結果（コンテナ名・現在の割当vCPU/メモリ・実測ピークCPU%/MEM%）を
入力すると、7.5.2・7.5.3の計算式で必要vCPU・必要メモリ・必要レプリカ数を
自動算出する。

## 8. 許容範囲の目安

一般的なUX基準。**日本語は1トークンあたりの文字数が英語より少ないため、
TPOT 50ms でも体感はやや遅い。日本語主体なら TPOT 30ms 以内を目標とする。**

| 指標 | 快適 | 許容 | 不可 |
|---|---|---|---|
| **TTFT** | < 1秒 | < 3秒 | > 5秒 |
| **TPOT** | < 30ms（33 tok/s） | < 50ms（20 tok/s） | > 100ms |
| エラー率 | 0% | < 0.1% | > 1% |

> **TTFT/TPOTが取得できない場合の代替基準（E2Eベース）**：LiteLLM側からTTFT/Duration
> が取得できない環境では、**ベースライン（最小並列数、通常は同時実行1）のE2Eに対する
> 倍率**で判定する。出力トークン数が異なるプロファイル間でも比較可能にするため、
> 絶対時間ではなく相対倍率を基準とする。

| 指標 | 快適 | 許容 | 飽和 | 不可 |
|---|---|---|---|---|
| **E2E（ベースライン比）** | < 1.5倍 | < 3倍 | < 5倍 | ≥ 5倍 |
| エラー率 | 0% | < 0.1% | < 1% | ≥ 1% |

## 10. 収容ユーザー数の換算

飽和点から実際の収容人数を算出する。

```
収容ユーザー数 ≈ 実効同時実行数 × (思考時間 + 1リクエスト所要時間) ÷ 1リクエスト所要時間
```

**計算例**
```
実効同時実行数        = 20（許容点）
1リクエストの所要時間  = 15秒
ユーザーの思考時間     = 60秒/回

収容ユーザー数 ≈ 20 × (60 + 15) ÷ 15 = 約100人
```

> **重要**: 「同時実行20 = 同時利用者20人」ではない。思考時間を含めると
> **数倍のユーザーを収容できる**。この換算式がStep2以降のサイジング根拠となる。
