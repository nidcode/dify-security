# 11. ログの保存とローテーション

監査・トラブル対応に使うログを、コンテナ内ではなく**ホストのディレクトリに保存**し、
logrotate で**日次ローテーション**する。あわせて、Docker 自身のログ (`/var/lib/docker`) に
上限を設け、ディスクを使い切らないようにする。

置き換え: `<TEAM>` `<DIFY_HOST>` `<GATEWAY_HOST>` `<LITELLM_HOST>` `<REPO_DIR>`。

> 新しく作る Dify インスタンス (`make dify-new`) は、作成時から同じ構成になる。
> この手順書の「初回適用」は、**この仕組みを入れる前から動いている環境**に対して各VMで1回だけ行う。

---

## 初回適用 (既存環境・各VMで1回)

> ⚠️ **メンテナンス時間帯に実施すること。** Docker の再起動とコンテナの作り直しで、
> そのVMのサービスが数分止まる。sudo のパスワードを求められる。

VMごとに次の①→②を行う (順番は問わない)。`<役割>` は Dify VM なら `dify`、Gateway VM なら
`gateway`、LiteLLM VM なら `litellm`。

### ① 変更内容の確認 (何も変更しない)

```bash
ssh <対象VM>
cd <REPO_DIR>
git pull
bash scripts/log-setup.sh <役割>
```

表示の見方:

- `1. Docker ログの上限`: `上限なし → ... を設定` なら②で Docker が再起動する。`設定済み` なら再起動しない
- `2. logrotate`: `新規に配置` / `配置済み` のどちらでもよい
- `3. ログの保存先と反映`: 反映されるインスタンス (Dify VM) が漏れなく表示されているか確認する
- `⚠` が出た場合: 内容を控えてベンダーに連絡 (実行してよいか判断を仰ぐ)

### ② 実行

```bash
bash scripts/log-setup.sh <役割> --apply
```

> `sudo bash ...` のように**全体を sudo で実行しないこと** (実行を拒否する)。必要な箇所だけ
> スクリプトが sudo を使い、パスワードを求める。

最後に `✅ 完了。` と表示されればOK。続けて表示される確認コマンドを実行し、次を確認する:

- 全コンテナに上限 (`10m`) が表示される
- ログファイルが作られている (Dify VM / Gateway VM)

その後、「日常点検」の手順書①で全サービスが `running`/`healthy` であることを確認する。

---

## 保持期間の変更

保持期間は各VMの `/etc/logrotate.d/` のファイルで、コンポーネントごとに設定する
(既定は日次ローテーション・90日分)。`rotate` の数字 (= 日数) を変更する。

```bash
sudo vi /etc/logrotate.d/dify-app      # 例: rotate 90 → rotate 365
sudo logrotate -d /etc/logrotate.d/dify-app   # 構文確認 (エラーが出なければOK)
```

`log-setup.sh` を再実行しても、編集したファイルは上書きされない。

---

## トラブルシュート

- ログファイルが作られない: そのインスタンスで `docker compose ps -a` を実行し、`log_permissions` が
  `exited (0)` か確認する。それ以外なら `docker compose logs log_permissions` を控えてベンダーに連絡。
- ディスクが逼迫している: 下記「付録」の保存先で `sudo du -sh` を実行して大きいものを特定し、
  保持期間の短縮を検討する。

---

## 付録: ログの保存先一覧

| VM | ログ | 保存先 | ローテーション設定 |
|---|---|---|---|
| Dify | Dify 本体 (api / api_websocket / worker / worker_beat) | `dify/instances/<TEAM>/logs/<サービス名>/server.log` | `/etc/logrotate.d/dify-app` |
| Dify | インスタンス内 nginx (アクセス / エラー) | `dify/instances/<TEAM>/logs/nginx/` | `/etc/logrotate.d/dify-nginx` |
| Dify | squid (ssrf_proxy / agent_ssrf_proxy / model_egress_guard) | `dify/instances/<TEAM>/logs/<サービス名>/` | `/etc/logrotate.d/dify-squid` |
| Gateway | front-nginx (アクセス / エラー) | `<REPO_DIR>/logs/gateway/nginx/` | `/etc/logrotate.d/gateway-nginx` |
| 全VM | 上記以外のコンテナの標準出力 (DB・Redis・Keycloak・oauth2-proxy・LiteLLM 等) | Docker のログ (`docker compose logs` で参照) | コンテナごとに 10MB × 5世代 (`/etc/docker/daemon.json`)。**コンテナを作り直すと消える** |

- ホストに保存したログは、「バックアップとリストア」の手順書のファイル一式に含まれる
  (Dify はインスタンスのフォルダごと、Gateway は `logs` を対象に追加済み)。
- ログのディレクトリは各サービスの書き込みユーザーが所有し、グループが運用ユーザーになる
  (setgid)。運用ユーザーで読めるため、バックアップの `tar` で読み飛ばされない。
- 別ディスクに保存したい場合は、`dify/instances/<TEAM>/logs` や `<REPO_DIR>/logs` を
  別ディスクへのシンボリックリンク / マウントにする (ベンダーに相談)。
