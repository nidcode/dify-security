# 3. バックアップとリストア

**目的: VM自体が失われても環境を復旧できること。** そのため次の3段階を扱う。

1. **バックアップ**: DB (`pg_dump`) + **サービスを動かすのに必要な全ファイル** (`tar`) を
   ローカルの `<BACKUP_DIR>` に保存。DBは軽量なので日次、Difyのファイル一式は容量が
   大きくなりやすいため週次を推奨 (詳細は末尾「実行頻度・世代管理」)
2. **オフサイトへの複製**: `<BACKUP_DIR>` の中身を、VMの外(クラウドストレージ等)にも複製する
   (ローカルにしか無いと、VMごと失われたときにバックアップも一緒に失われるため必須)
3. **リストア**: (a)同一VM上でのデータ復旧、または (b)VMを新規構築しての完全復旧

## 各VMのバックアップ対象一覧

| VM | 対象データ | 方式 | 頻度 | 除外・備考 |
|---|---|---|---|---|
| Dify VM (インスタンスごと) | DB (`dify`) | `pg_dump` | 日次 | - |
| Dify VM (インスタンスごと) | ファイル一式 (.env・compose定義一式・アップロードファイル・プラグイン・ベクトルDB) | `tar` (Weaviateのみ一時停止) | 週次 | Redis・Postgres生ファイル・sandboxの一時データは除外 (Redisは再構築可能なため対象外) |
| Gateway VM | DB (`keycloak`) | `pg_dump` | 日次 | - |
| Gateway VM | ファイル一式 (.env・compose定義・運用スクリプト・nginx設定一式・TLS証明書) | `tar` | 日次 | - |
| LiteLLM VM | DB (`litellm`) | `pg_dump` | 日次 | - |
| LiteLLM VM | ファイル一式 (.env・compose定義・config.yaml・Vertex WIF資格情報) | `tar` | 日次 | - |

> **設計方針**: 完全復旧は `git clone` に頼らない。理由は、バックアップ取得後にリポジトリ側で
> Difyのバージョンを上げる等の更新が入っていた場合、`git clone` で取得した最新のテンプレートは
> バックアップしたDBのスキーマ(バージョン)と食い違い、リストア時に意図しないマイグレーションや
> 起動失敗を招くため。そこで**バックアップ自体に、そのサービスを動かすのに必要な設定ファイル
> (docker-compose.yaml・nginx設定・スクリプト等) を丸ごと含める**ことで、
> リストアはバックアップの展開だけで完結し、リポジトリの現在の状態に依存しない。

置き換え: `<TEAM>` `<DIFY_HOST>` `<GATEWAY_HOST>` `<LITELLM_HOST>` `<BACKUP_DIR>` `<REPO_DIR>`
`<REPO_URL>` `<OFFSITE_REMOTE>`。

> ⚠️ **リストアは実行中のデータを上書きする破壊的操作です。** 各VMの「リストア」実行前に、
> 必ず ①対象のVM/インスタンス名が合っているか ②今まさに戻す必要がある状況か
> (誤って正常なデータを古いバックアップで上書きしないか) を指差し確認してください。
> 可能であれば実行直前にもう一度その時点のバックアップを取ってから進めると安全です。

> ⚠️ **VMを新規構築する際は、可能な限り同じIPアドレスを再利用すること。** IPが変わると、
> Gateway側の各チームのnginx設定 (Dify VMのIPを直接指定している) や、Difyのモデルプロバイダ
> 設定 (LiteLLM VMのIPを直接指定していて、Dify管理画面からチームごとに再設定が必要) など、
> 複数箇所の追随修正が発生する。

## オフサイトへの複製

`<BACKUP_DIR>` の中身をVMの外 (`<OFFSITE_REMOTE>`) にも複製する。ローカルディスクにしか
無いと、VMごと失われたときにバックアップも一緒に失われるため必須の手順。転送先には
`rclone` がS3・GCS・Azure・SFTP等どのストレージにも同じコマンドで対応できるため利用する。

```bash
# 各VMで一度だけ (パッケージがあれば `apt-get install -y rclone` でも可)
curl https://rclone.org/install.sh | sudo bash
rclone config   # 対話形式で "<OFFSITE_REMOTE>" という名前の転送先を設定する
```

以降、各VMのバックアップ手順にある「オフサイトへ複製」のコマンドを毎回実行する。

## ① Dify VM (インスタンス `<TEAM>` ごと)

各インスタンスのフォルダ (`dify/instances/<TEAM>/`) は `docker-compose.yaml` ごと複製されて
自己完結しているため、これを丸ごとバックアップに含めればリポジトリの現在の状態に依存しない。

### バックアップ

```bash
ssh <DIFY_HOST>
mkdir -p <BACKUP_DIR>
cd <REPO_DIR>/dify/instances/<TEAM>

# DB (推奨頻度: 日次。軽量なので世代数を多めに残せる)
docker compose exec -e PGPASSWORD=$(grep '^DB_PASSWORD=' .env | cut -d= -f2) db_postgres \
  pg_dump -U postgres --clean --if-exists dify | gzip > <BACKUP_DIR>/dify-<TEAM>-db-$(date +%F).sql.gz

# インスタンスフォルダを丸ごと (推奨頻度: 週次。アップロードファイル・ベクトルDBを含み
# 容量が大きくなりやすいため、DBより頻度を下げて世代数を絞る)。
# .env / docker-compose定義一式 / nginx・ssrf_proxy等の設定 / アップロードファイル / プラグイン / ベクトルDB。
# ※ volumes/db, volumes/redis, volumes/sandbox は除外 (DBはpg_dump側で取得済み・残りは再構築可能な一時データ)
#
# Weaviate(ベクトルDB)は稼働中のファイルを直接コピーすると不整合になり得るため
# (Postgresをpg_dumpにした理由と同じ)、コピー中だけ一時停止する。
# ナレッジベース検索のみ数十秒〜数分止まる (通常のチャット応答は継続する)。
docker compose stop weaviate

tar czf <BACKUP_DIR>/dify-<TEAM>-files-$(date +%F).tar.gz --ignore-failed-read \
  --exclude='volumes/db' --exclude='volumes/redis' --exclude='volumes/sandbox' \
  .

docker compose start weaviate
```

バックアップ確認 (サイズが `0` や数百バイトなら失敗の可能性。ベンダーに連絡):

```bash
ls -lh <BACKUP_DIR>/dify-<TEAM>-*-$(date +%F)*
```

オフサイトへ複製:

```bash
rclone copy <BACKUP_DIR> <OFFSITE_REMOTE>:dify-backup/<DIFY_HOST>/ --include "*-$(date +%F)*"
```

### リストア (同一VM上・データ破損時)

上部の ⚠️ 「実行前の注意」を確認してから進めてください。

最新のバックアップファイルを確認する (表示された日付が意図したものか必ず確認):

```bash
ssh <DIFY_HOST>
cd <REPO_DIR>/dify/instances/<TEAM>
DB_BAK=$(ls -t <BACKUP_DIR>/dify-<TEAM>-db-*.sql.gz | head -1)
FILES_BAK=$(ls -t <BACKUP_DIR>/dify-<TEAM>-files-*.tar.gz | head -1)
echo "DB: $DB_BAK"
echo "ファイル: $FILES_BAK"
```

上記2つのファイル名 (日付) が想定どおりであることを確認したら実行:

```bash
docker compose down
tar xzf "$FILES_BAK"

docker compose up -d db_postgres
docker compose ps   # db_postgres が healthy になるまで待つ

gunzip -c "$DB_BAK" | \
  docker compose exec -T -e PGPASSWORD=$(grep '^DB_PASSWORD=' .env | cut -d= -f2) db_postgres \
  psql -U postgres -d dify

docker compose up -d
docker compose ps   # 全サービスが running/healthy か確認
```

### 完全復旧 (VM自体を失った場合)

新しいVMを用意した後の手順 (OSは既存VMと同じディストリビューションを推奨)。
**gitリポジトリは不要**(バックアップに含まれる`docker-compose.yaml`一式がそのまま使える)。

```bash
# 1. Docker Engineをインストール
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $(whoami)   # 反映には再ログインが必要

# 2. オフサイトからバックアップを取得
curl https://rclone.org/install.sh | sudo bash
rclone config   # <OFFSITE_REMOTE> を再設定
mkdir -p <BACKUP_DIR>
rclone copy <OFFSITE_REMOTE>:dify-backup/<DIFY_HOST>/ <BACKUP_DIR>

# 3. インスタンスフォルダを復元 (バックアップの中身がそのままdocker-compose.yaml一式になる)
mkdir -p <REPO_DIR>/dify/instances/<TEAM>
cd <REPO_DIR>/dify/instances/<TEAM>
tar xzf <BACKUP_DIR>/dify-<TEAM>-files-最新日付.tar.gz
```

以降は上記「リストア (同一VM上・データ破損時)」の `docker compose up -d db_postgres`
以降と同じ手順 (DB復元 → `docker compose up -d`) を実行する。複数チームが同居していた場合は、
手順3以降をチームの数だけ繰り返す。

> 今後このVMで `make dify-new` 等の運用コマンド(このリポジトリの他の手順書)を使いたい場合は、
> 別途 `git clone <REPO_URL> <REPO_DIR>` してリポジトリ化すること。上で復元した
> `dify/instances/<TEAM>/` はそのままリポジトリ配下に置けば良く、サービスの復旧自体には影響しない。

## ② Gateway VM (Keycloak)

Keycloak停止は**全チームのログイン処理**に影響するため、メンテナンス時間帯に実施する
(front-nginxは止めないため、ログイン済みセッションへの影響は限定的)。

### バックアップ (無停止)

```bash
ssh <GATEWAY_HOST>
mkdir -p <BACKUP_DIR>
cd <REPO_DIR>

# DB (推奨頻度: 日次)
docker compose -p aiop-gateway --env-file .env -f compose.gateway.yaml \
  exec -e PGPASSWORD=$(grep '^KEYCLOAK_DB_PASSWORD=' .env | cut -d= -f2) keycloak-db \
  pg_dump -U keycloak --clean --if-exists keycloak | gzip > <BACKUP_DIR>/keycloak-db-$(date +%F).sql.gz

# ファイル一式 (推奨頻度: 日次。設定ファイルのみで小さいため)
# .env / compose定義 / 運用スクリプト / nginx設定一式 / チーム別oauth2-proxy定義 / TLS証明書
tar czf <BACKUP_DIR>/gateway-files-$(date +%F).tar.gz --ignore-failed-read \
  .env compose.gateway.yaml Makefile scripts \
  gateway/oauth2-proxies.gateway.yaml gateway/nginx gateway/certs
```

バックアップ確認:

```bash
ls -lh <BACKUP_DIR>/*-$(date +%F)*
```

オフサイトへ複製:

```bash
rclone copy <BACKUP_DIR> <OFFSITE_REMOTE>:gateway-backup/ --include "*-$(date +%F)*"
```

### リストア (同一VM上・データ破損時)

上部の ⚠️ 「実行前の注意」を確認してから進めてください(Keycloak停止の影響は本セクション冒頭を参照)。

最新のバックアップファイルを確認する (表示された日付が意図したものか必ず確認):

```bash
ssh <GATEWAY_HOST>
cd <REPO_DIR>
GW="docker compose -p aiop-gateway --env-file .env -f compose.gateway.yaml"
DB_BAK=$(ls -t <BACKUP_DIR>/keycloak-db-*.sql.gz | head -1)
FILES_BAK=$(ls -t <BACKUP_DIR>/gateway-files-*.tar.gz | head -1)
echo "DB: $DB_BAK"
echo "ファイル: $FILES_BAK"
```

上記2つのファイル名 (日付) が想定どおりであることを確認したら実行:

```bash
tar xzf "$FILES_BAK"

$GW stop keycloak
$GW up -d keycloak-db
$GW ps   # keycloak-db が healthy になるまで待つ

gunzip -c "$DB_BAK" | \
  $GW exec -T -e PGPASSWORD=$(grep '^KEYCLOAK_DB_PASSWORD=' .env | cut -d= -f2) keycloak-db \
  psql -U keycloak -d keycloak

make gateway-up
$GW ps   # 全サービスが running/healthy か確認
```

### 完全復旧 (VM自体を失った場合)

新しいVMを用意した後の手順。**gitリポジトリは不要**(バックアップに`compose.gateway.yaml`・
`Makefile`・`scripts/`一式が含まれるため、展開するだけで`make gateway-up`が使える)。

```bash
# 1. Docker Engineをインストール
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $(whoami)

# 2. オフサイトからバックアップを取得
curl https://rclone.org/install.sh | sudo bash
rclone config
mkdir -p <BACKUP_DIR>
rclone copy <OFFSITE_REMOTE>:gateway-backup/ <BACKUP_DIR>

# 3. リポジトリディレクトリを復元 (バックアップの中身がそのままリポジトリ構成になる)
mkdir -p <REPO_DIR>
cd <REPO_DIR>
tar xzf <BACKUP_DIR>/gateway-files-最新日付.tar.gz
```

以降は上記「リストア (同一VM上・データ破損時)」の `$GW up -d keycloak-db` 以降と同じ手順
(DB復元 → `make gateway-up`) を実行する。

> Dify VMのIPが変わっていなければ、復元される `gateway/nginx/templates/` の内容
> (各チームのDify接続先) はそのまま使える。IPが変わった場合は該当チームの
> `.conf.template` を編集し `make gateway-up` で反映すること。
>
> 今後 `git pull` でベンダーの更新を取り込みたい場合は、別途 `git clone <REPO_URL>` して
> リポジトリ化すること (この方法で復元した `<REPO_DIR>` はバックアップ時点のファイルそのままで、
> git管理下にはない)。

## 実行頻度・世代管理

DBダンプは軽量なので**日次**、Difyのファイル一式(アップロード・ベクトルDB)は容量が
大きくなりやすいため**週次**を推奨する(Gateway/LiteLLMのファイル一式は設定ファイルのみで
小さいため、DBと同じ日次でよい)。

世代管理は日付ではなく**世代数**で行う(頻度が異なっても運用がぶれないため)。各VMに
以下の関数を用意しておく (`.bashrc` やcron実行用スクリプトに追記):

```bash
# 新しい方から $2 世代だけ残し、それより古いものを削除する
keep_generations() {
  ls -t $1 2>/dev/null | tail -n +$(($2 + 1)) | xargs -r rm -f
}
```

例 (Dify VM のcron設定。DBは14世代=2週間分、ファイルは4世代=1ヶ月分を保持):

```cron
# DB: 毎日3時
0 3 * * * cd <REPO_DIR>/dify/instances/<TEAM> && docker compose exec -e PGPASSWORD=$(grep '^DB_PASSWORD=' .env | cut -d= -f2) db_postgres pg_dump -U postgres --clean --if-exists dify | gzip > <BACKUP_DIR>/dify-<TEAM>-db-$(date +\%F).sql.gz && rclone copy <BACKUP_DIR> <OFFSITE_REMOTE>:dify-backup/<DIFY_HOST>/ --include "*-$(date +\%F)*" && keep_generations "<BACKUP_DIR>/dify-<TEAM>-db-*.sql.gz" 14

# ファイル一式: 毎週日曜4時
0 4 * * 0 cd <REPO_DIR>/dify/instances/<TEAM> && tar czf <BACKUP_DIR>/dify-<TEAM>-files-$(date +\%F).tar.gz --ignore-failed-read --exclude='volumes/db' --exclude='volumes/redis' --exclude='volumes/sandbox' . && rclone copy <BACKUP_DIR> <OFFSITE_REMOTE>:dify-backup/<DIFY_HOST>/ --include "*-$(date +\%F)*" && keep_generations "<BACKUP_DIR>/dify-<TEAM>-files-*.tar.gz" 4
```

Gateway/LiteLLM VMはDB・ファイルとも同じ頻度(毎日)・世代数(目安14)でよい。

オフサイト側の世代管理は使用するストレージの機能 (ライフサイクルルール等) に合わせて
別途設定する (`rclone`側での一括削除は誤操作リスクがあるため推奨しない)。

上記の世代数・頻度は目安。データ量や復旧要件(RPO)に応じて調整すること。
