# 3. バックアップとリストア

**目的: VM自体が失われても環境を復旧できること。** そのため次の3段階を扱う。

1. **バックアップ**: DB (`pg_dump`) + **サービスを動かすのに必要な全ファイル** (`tar`) を
   ローカルの `<BACKUP_DIR>` に保存。DBは軽量なので日次、Difyのファイル一式は容量が
   大きくなりやすいため週次を推奨 (詳細は末尾「実行頻度・世代管理」)
2. **オフサイトへの複製**: `<BACKUP_DIR>` の中身を、VMの外(クラウドストレージ等)にも複製する
   (ローカルにしか無いと、VMごと失われたときにバックアップも一緒に失われるため必須)
3. **リストア**: (a)同一VM上でのデータ復旧、または (b)VMを新規構築しての完全復旧

## 各VMのバックアップ対象一覧

| VM | 対象データ | 方式 | 頻度 | 除外・備考 |
|---|---|---|---|---|
| Dify VM (インスタンスごと) | DB (`dify`) | `pg_dump` | 日次 | - |
| Dify VM (インスタンスごと) | ファイル一式 (.env・compose定義一式・アップロードファイル・プラグイン・ベクトルDB・ログ) | `tar` (Weaviateのみ一時停止) | 週次 | Redis・Postgres生ファイル・sandboxの一時データは除外 (Redisは再構築可能なため対象外) |
| Gateway VM | DB (`keycloak`) | `pg_dump` | 日次 | - |
| Gateway VM | ファイル一式 (.env・compose定義一式・運用スクリプト・nginx設定一式・TLS証明書・ログ) | `tar` | 日次 | - |
| LiteLLM VM | DB (`litellm`) | `pg_dump` | 日次 | - |
| LiteLLM VM | ファイル一式 (.env・compose定義・config.yaml・Vertex WIF資格情報) | `tar` | 日次 | - |

> **設計方針**: 完全復旧は `git clone` に頼らない。理由は、バックアップ取得後にリポジトリ側で
> Difyのバージョンを上げる等の更新が入っていた場合、`git clone` で取得した最新のテンプレートは
> バックアップしたDBのスキーマ(バージョン)と食い違い、リストア時に意図しないマイグレーションや
> 起動失敗を招くため。そこで**バックアップ自体に、そのサービスを動かすのに必要な設定ファイル
> (docker-compose.yaml・nginx設定・スクリプト等) を丸ごと含める**ことで、
> リストアはバックアップの展開だけで完結し、リポジトリの現在の状態に依存しない。

置き換え: `<TEAM>` `<DIFY_HOST>` `<GATEWAY_HOST>` `<LITELLM_HOST>` `<BACKUP_DIR>` `<REPO_DIR>`
`<REPO_URL>` `<OFFSITE_REMOTE>`。

> ⚠️ **リストアは実行中のデータを上書きする破壊的操作です。** 各VMの「リストア」実行前に、
> 必ず ①対象のVM/インスタンス名が合っているか ②今まさに戻す必要がある状況か
> (誤って正常なデータを古いバックアップで上書きしないか) を指差し確認してください。
> 可能であれば実行直前にもう一度その時点のバックアップを取ってから進めると安全です。

> ⚠️ **VMを新規構築する際は、可能な限り同じIPアドレスを再利用すること。** IPが変わると、
> Gateway側の各チームのnginx設定 (Dify VMのIPを直接指定している) や、Difyのモデルプロバイダ
> 設定 (LiteLLM VMのIPを直接指定していて、Dify管理画面からチームごとに再設定が必要) など、
> 複数箇所の追随修正が発生する。

バックアップは各VMで `scripts/backup.sh` (取得・確認・古い世代の削除) と `rclone` (オフサイトへの
複製) を cron から定期実行して取る。初回に「オフサイトへの複製」と「定期実行の設定」を行えば、
以後の手作業は不要。手動で取り直す場合 (作業前など) は各VMの「バックアップ」のコマンドを実行する。

## オフサイトへの複製

`<BACKUP_DIR>` の中身をVMの外 (`<OFFSITE_REMOTE>`) にも複製する。ローカルディスクにしか
無いと、VMごと失われたときにバックアップも一緒に失われるため必須の手順。転送先には
`rclone` がS3・GCS・Azure・SFTP等どのストレージにも同じコマンドで対応できるため利用する。

```bash
# 各VMで一度だけ (パッケージがあれば `apt-get install -y rclone` でも可)
curl https://rclone.org/install.sh | sudo bash
rclone config   # 対話形式で "<OFFSITE_REMOTE>" という名前の転送先を設定する
```

続けて、各VMの `<REPO_DIR>/.env` に保存先 `BACKUP_DIR=<BACKUP_DIR>` を設定する
(`scripts/backup.sh` が使う。既にある行は値を書き換える)。

複製は各VMの「バックアップ」にある `rclone copy` で行う (定期実行は末尾「定期実行の設定」)。
`rclone copy` は複製先に無い・変わったファイルだけを送るため、`<BACKUP_DIR>` を丸ごと指定してよい。
複製先は VM ごとに次のとおり (各VMの「完全復旧」はここから取得する):

| VM | 複製先 |
|---|---|
| Dify VM | `<OFFSITE_REMOTE>:dify-backup/<DIFY_HOST>/` |
| Gateway VM | `<OFFSITE_REMOTE>:gateway-backup/` |
| LiteLLM VM | `<OFFSITE_REMOTE>:litellm-backup/` |

## ① Dify VM (インスタンス `<TEAM>` ごと)

各インスタンスのフォルダ (`dify/instances/<TEAM>/`) は `docker-compose.yaml` ごと複製されて
自己完結しているため、これを丸ごとバックアップに含めればリポジトリの現在の状態に依存しない。

### バックアップ

```bash
ssh <DIFY_HOST>
cd <REPO_DIR>

bash scripts/backup.sh dify-db <TEAM>      # DB (日次)
bash scripts/backup.sh dify-files <TEAM>   # インスタンスフォルダ一式 (週次)

# オフサイトへ複製
rclone copy <BACKUP_DIR> <OFFSITE_REMOTE>:dify-backup/<DIFY_HOST>/ --include "*.gz"
```

`backup.sh` の最後に `✅ 完了` と表示されれば、取得と確認は済んでいる。`❌` が出た場合
(`rclone` がエラーを表示した場合も) は、表示を控えてベンダーに連絡する。`<TEAM>` を省略すると全インスタンスを取得する。

- DB: `<BACKUP_DIR>/dify-<TEAM>-db-<日付>.sql.gz`
- インスタンスフォルダ一式: `<BACKUP_DIR>/dify-<TEAM>-files-<日付>.tar.gz`
  (.env / docker-compose定義一式 / nginx・ssrf_proxy等の設定 / アップロードファイル / プラグイン /
  ベクトルDB / ログ)。`volumes/db` `volumes/redis` `volumes/sandbox` は除外する (DBは上のダンプで
  取得済み・残りは再構築できる一時データ)。
- ファイル一式の取得中は Weaviate (ベクトルDB) を一時停止する (稼働中のファイルをコピーすると
  不整合になり得るため)。ナレッジベース検索のみ数十秒〜数分止まる (通常のチャット応答は継続する)。

### リストア (同一VM上・データ破損時)

上部の ⚠️ 「実行前の注意」を確認してから進めてください。

最新のバックアップファイルを確認する (表示された日付が意図したものか必ず確認):

```bash
ssh <DIFY_HOST>
cd <REPO_DIR>/dify/instances/<TEAM>
DB_BAK=$(ls -t <BACKUP_DIR>/dify-<TEAM>-db-*.sql.gz | head -1)
FILES_BAK=$(ls -t <BACKUP_DIR>/dify-<TEAM>-files-*.tar.gz | head -1)
echo "DB: $DB_BAK"
echo "ファイル: $FILES_BAK"
```

上記2つのファイル名 (日付) が想定どおりであることを確認したら実行:

```bash
docker compose down
# 展開もコンテナ内の root で行う (root 所有のファイルを上書きし、各ファイルの所有者を元どおりに戻すため)。
# ログ (logs/) は展開しない: 現在のログはバックアップ以降の記録を含むため
docker run --rm -i -v "$PWD":/dst -w /dst busybox \
  tar xzf - --numeric-owner --exclude=./logs < "$FILES_BAK"

docker compose up -d db_postgres
docker compose ps   # db_postgres が healthy になるまで待つ

gunzip -c "$DB_BAK" | \
  docker compose exec -T -e PGPASSWORD=$(grep '^DB_PASSWORD=' .env | cut -d= -f2) db_postgres \
  psql -U postgres -d dify

docker compose up -d
docker compose ps   # 全サービスが running/healthy か確認
```

### 完全復旧 (VM自体を失った場合)

新しいVMを用意した後の手順 (OSは既存VMと同じディストリビューションを推奨)。
**gitリポジトリは不要**(バックアップに含まれる`docker-compose.yaml`一式がそのまま使える)。

```bash
# 1. Docker Engineをインストール
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $(whoami)   # 反映には再ログインが必要

# 2. オフサイトからバックアップを取得
curl https://rclone.org/install.sh | sudo bash
rclone config   # <OFFSITE_REMOTE> を再設定
mkdir -p <BACKUP_DIR>
rclone copy <OFFSITE_REMOTE>:dify-backup/<DIFY_HOST>/ <BACKUP_DIR>

# 3. インスタンスフォルダを復元 (バックアップの中身がそのままdocker-compose.yaml一式になる)
mkdir -p <REPO_DIR>/dify/instances/<TEAM>
cd <REPO_DIR>/dify/instances/<TEAM>
docker run --rm -i -v "$PWD":/dst -w /dst busybox \
  tar xzf - --numeric-owner < <BACKUP_DIR>/dify-<TEAM>-files-最新日付.tar.gz

# 4. 旧VMの運用ユーザーのファイルを、このVMの運用ユーザーに付け替える
#    (ユーザーID が旧VMと違うと .env 等を読めないため。同じなら何も変わらない。
#     root やコンテナ用ユーザーが所有するファイルは対象外)
sudo chown -R --from="$(stat -c %u:%g .env)" "$(id -u):$(id -g)" .
```

以降は上記「リストア (同一VM上・データ破損時)」の `docker compose up -d db_postgres`
以降と同じ手順 (DB復元 → `docker compose up -d`) を実行する。複数チームが同居していた場合は、
手順3〜4をチームの数だけ繰り返す。

> 今後このVMで定期バックアップ (`scripts/backup.sh`) や `make dify-new` 等の運用コマンド
> (このリポジトリの他の手順書) を使うため、別途 `git clone <REPO_URL> <REPO_DIR>` してリポジトリ化し、
> 「オフサイトへの複製」の `BACKUP_DIR` の設定と「定期実行の設定」をやり直すこと。上で復元した
> `dify/instances/<TEAM>/` はそのままリポジトリ配下に置けば良く、サービスの復旧自体には影響しない。

## ② Gateway VM (Keycloak)

Keycloak停止は**全チームのログイン処理**に影響するため、メンテナンス時間帯に実施する
(front-nginxは止めないため、ログイン済みセッションへの影響は限定的)。

### バックアップ (無停止)

```bash
ssh <GATEWAY_HOST>
cd <REPO_DIR>
bash scripts/backup.sh gateway

# オフサイトへ複製
rclone copy <BACKUP_DIR> <OFFSITE_REMOTE>:gateway-backup/ --include "*.gz"
```

`backup.sh` の最後に `✅ 完了` と表示されれば、取得と確認は済んでいる。`❌` が出た場合
(`rclone` がエラーを表示した場合も) は、表示を控えてベンダーに連絡する。

- DB: `<BACKUP_DIR>/keycloak-db-<日付>.sql.gz`
- ファイル一式: `<BACKUP_DIR>/gateway-files-<日付>.tar.gz`
  (.env / compose定義一式 / 運用スクリプト / ログ / nginx設定一式 / チーム別oauth2-proxy定義 / TLS証明書)

### リストア (同一VM上・データ破損時)

上部の ⚠️ 「実行前の注意」を確認してから進めてください(Keycloak停止の影響は本セクション冒頭を参照)。

最新のバックアップファイルを確認する (表示された日付が意図したものか必ず確認):

```bash
ssh <GATEWAY_HOST>
cd <REPO_DIR>
DB_BAK=$(ls -t <BACKUP_DIR>/keycloak-db-*.sql.gz | head -1)
FILES_BAK=$(ls -t <BACKUP_DIR>/gateway-files-*.tar.gz | head -1)
echo "DB: $DB_BAK"
echo "ファイル: $FILES_BAK"
```

上記2つのファイル名 (日付) が想定どおりであることを確認したら実行:

```bash
# ログ (logs/) は展開しない: 現在のログはバックアップ以降の記録を含み、かつ各サービスの所有で上書きできないため
tar xzf "$FILES_BAK" --anchored --exclude=logs

make gateway-stop SVC=keycloak
make gateway-up SVC=keycloak-db
make gateway-ps   # keycloak-db が healthy になるまで待つ

gunzip -c "$DB_BAK" | make -s gateway-db-restore

make gateway-up
make gateway-ps   # 全サービスが running/healthy か確認
```

### 完全復旧 (VM自体を失った場合)

新しいVMを用意した後の手順。**gitリポジトリは不要**(バックアップに`compose.gateway.yaml`・
`Makefile`・`scripts/`一式が含まれるため、展開するだけで`make gateway-up`が使える)。

```bash
# 1. Docker Engineをインストール
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $(whoami)

# 2. オフサイトからバックアップを取得
curl https://rclone.org/install.sh | sudo bash
rclone config
mkdir -p <BACKUP_DIR>
rclone copy <OFFSITE_REMOTE>:gateway-backup/ <BACKUP_DIR>

# 3. リポジトリディレクトリを復元 (バックアップの中身がそのままリポジトリ構成になる)
mkdir -p <REPO_DIR>
cd <REPO_DIR>
tar xzf <BACKUP_DIR>/gateway-files-最新日付.tar.gz
```

以降は上記「リストア (同一VM上・データ破損時)」の `make gateway-up SVC=keycloak-db` 以降と同じ手順
(DB復元 → `make gateway-up`) を実行する。

> Dify VMのIPが変わっていなければ、復元される `gateway/nginx/templates/` の内容
> (各チームのDify接続先) はそのまま使える。IPが変わった場合は該当チームの
> `.conf.template` を編集し `make gateway-up` で反映すること。
>
> 定期バックアップは復元した `.env` と `scripts/` でそのまま動くため、「定期実行の設定」の
> cron を登録し直すこと。
>
> 今後 `git pull` でベンダーの更新を取り込みたい場合は、別途 `git clone <REPO_URL>` して
> リポジトリ化すること (この方法で復元した `<REPO_DIR>` はバックアップ時点のファイルそのままで、
> git管理下にはない)。

## ③ LiteLLM VM

LiteLLM は全Difyインスタンスの唯一のゲートウェイのため、停止は**全チームのLLM呼び出し**を
止める。バックアップ自体は無停止だが、リストアは短時間の停止を伴う。

### バックアップ (無停止)

```bash
ssh <LITELLM_HOST>
cd <REPO_DIR>
bash scripts/backup.sh litellm

# オフサイトへ複製
rclone copy <BACKUP_DIR> <OFFSITE_REMOTE>:litellm-backup/ --include "*.gz"
```

`backup.sh` の最後に `✅ 完了` と表示されれば、取得と確認は済んでいる。`❌` が出た場合
(`rclone` がエラーを表示した場合も) は、表示を控えてベンダーに連絡する。

- DB: `<BACKUP_DIR>/litellm-db-<日付>.sql.gz` (仮想キー・予算・チーム・画面から追加したモデル・利用ログ)
- ファイル一式: `<BACKUP_DIR>/litellm-files-<日付>.tar.gz`
  (.env / compose定義 / Makefile / モデル設定 / Vertex WIF資格情報)

### リストア (同一VM上・データ破損時)

上部の ⚠️ 「実行前の注意」を確認してから進めてください(LiteLLM停止の影響は本セクション冒頭を参照)。

```bash
ssh <LITELLM_HOST>
cd <REPO_DIR>
LL="docker compose -p aiop-litellm --env-file .env -f compose.litellm.yaml"
DB_BAK=$(ls -t <BACKUP_DIR>/litellm-db-*.sql.gz | head -1)
FILES_BAK=$(ls -t <BACKUP_DIR>/litellm-files-*.tar.gz | head -1)
echo "DB: $DB_BAK"
echo "ファイル: $FILES_BAK"
```

上記2つのファイル名 (日付) が想定どおりであることを確認したら実行:

```bash

$LL stop litellm
$LL up -d litellm-db
$LL ps   # litellm-db が healthy になるまで待つ

gunzip -c "$DB_BAK" | \
  $LL exec -T -e PGPASSWORD=$(grep '^LITELLM_DB_PASSWORD=' .env | cut -d= -f2) litellm-db \
  psql -U litellm -d litellm

$LL up -d
$LL ps   # 全サービスが running/healthy か確認
```

新しいVMを用意した後の手順。**gitリポジトリは不要**(バックアップに`compose.litellm.yaml`・
`Makefile`一式が含まれるため、展開するだけで起動できる)。

```bash
# 1. Docker Engineをインストール
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $(whoami)

# 2. オフサイトからバックアップを取得
curl https://rclone.org/install.sh | sudo bash
```

以降は上記「リストア (同一VM上・データ破損時)」の `$LL up -d litellm-db` 以降と同じ手順

> ⚠️ LiteLLM VMのIPが変わった場合、各Difyインスタンスのモデルプロバイダ設定

> 定期バックアップ (`scripts/backup.sh`) はバックアップに含まれないため、別途
> `git clone <REPO_URL>` してリポジトリ化してから (今後 `git pull` でベンダーの更新を取り込む
> 場合も同様)、「定期実行の設定」の cron を登録し直すこと。

## 定期実行の設定 (実行頻度・世代管理)

DBダンプは軽量なので**日次**、Difyのファイル一式(アップロード・ベクトルDB)は容量が
大きくなりやすいため**週次**とする(Gateway/LiteLLMのファイル一式は設定ファイルのみで
小さいため、DBと同じ日次)。

各VMで、運用ユーザーの cron に登録する (`crontab -e`)。実行結果は `<BACKUP_DIR>/backup.log` に残る。

```cron
# Dify VM: DB は毎日3時、ファイル一式は毎週日曜4時 (全インスタンス。インスタンスを追加しても変更不要)
#          オフサイトへの複製は毎日5時 (取得が済んだ後)
0 3 * * * cd <REPO_DIR> && bash scripts/backup.sh dify-db >> <BACKUP_DIR>/backup.log 2>&1
0 4 * * 0 cd <REPO_DIR> && bash scripts/backup.sh dify-files >> <BACKUP_DIR>/backup.log 2>&1
0 5 * * * rclone copy <BACKUP_DIR> <OFFSITE_REMOTE>:dify-backup/<DIFY_HOST>/ --include "*.gz" >> <BACKUP_DIR>/backup.log 2>&1

# Gateway VM: 毎日3時、オフサイトへの複製は毎日5時
0 3 * * * cd <REPO_DIR> && bash scripts/backup.sh gateway >> <BACKUP_DIR>/backup.log 2>&1
0 5 * * * rclone copy <BACKUP_DIR> <OFFSITE_REMOTE>:gateway-backup/ --include "*.gz" >> <BACKUP_DIR>/backup.log 2>&1

# LiteLLM VM: 毎日3時、オフサイトへの複製は毎日5時
0 3 * * * cd <REPO_DIR> && bash scripts/backup.sh litellm >> <BACKUP_DIR>/backup.log 2>&1
0 5 * * * rclone copy <BACKUP_DIR> <OFFSITE_REMOTE>:litellm-backup/ --include "*.gz" >> <BACKUP_DIR>/backup.log 2>&1
```

世代管理は日付ではなく**世代数**で行い、`scripts/backup.sh` が取得に成功したときに古いものを
削除する (取得に失敗した日は消さない)。既定は DB と Gateway/LiteLLM のファイル一式が14世代
(2週間分)、Difyのファイル一式が4世代 (1ヶ月分)。変える場合は `<REPO_DIR>/.env` の
`BACKUP_KEEP` / `BACKUP_KEEP_DIFY_FILES` に世代数を設定する。
バージョンアップ前のバックアップ (ファイル名に `pre-upgrade` を含む) は削除しない
(不要になったら手で削除する)。

オフサイト側の世代管理は使用するストレージの機能 (ライフサイクルルール等) に合わせて
別途設定する (`rclone`側での一括削除は誤操作リスクがあるため推奨しない)。

上記の世代数・頻度は目安。データ量や復旧要件(RPO)に応じて調整すること。
